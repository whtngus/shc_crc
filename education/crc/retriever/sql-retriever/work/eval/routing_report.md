## 6. 왜 틀렸나(LLM reason 분석)

- 19건 모두 reason이 "합계/집계가 필요하므로 정형쿼리로는 답할 수 없음" 또는 "정형쿼리로 제공되지 않음" 형태임  
  - 예: F05-1 "업종별 사용액 합계를 요구하므로 정형쿼리로는 답할 수 없으며 …"  
  - 예: F08-2 "날짜별 일별 사용 금액은 정형쿼리로 제공되지 않으며 …"(FQ-08이 바로 그 내용인데도)  
- 원인 추정 1 — **예시 2의 reason 문장**: "가맹점별 합계와 순위가 필요해 정형쿼리로는 답할 수 없음".  
  모델이 "합계가 필요하면 NL2SQL"이라는 규칙으로 배운 것으로 보임. FQ-04, FQ-05는 이미 합계를 내는 쿼리임  
- 원인 추정 2 — **정형쿼리 표가 너무 짧음**: 설명 한 줄과 결과 단위만 있고, 어떤 컬럼을 돌려주는지,  
  이미 합산·정렬됐는지가 없음. 그래서 "업종별 사용액"이 합계까지 해 준다는 것을 모델이 모름  
- 원인 추정 3 — **동의어**: "날짜별, 하루하루, 일자별, 매일"(FQ-08), "카테고리별, 어떤 업종에서"(FQ-05)를  
  정형쿼리 이름과 잇지 못함. 반면 "가입일, 연령대, 카드, 연체"처럼 표의 낱말과 같은 질문은 거의 다 맞힘  
- 원인 추정 4 — **기간이 붙은 질문**: "최근 6개월", "최근 90일"처럼 기간을 말하면 NL2SQL로 가는 경향이 있음  
  (DIRECT 중 기간을 말한 8건 중 6건: F03-2, F03-5, F04-2, F05-4, F08-2, F08-4).  
  정형쿼리 기간과 같은 기간인데도 필터가 필요하다고 판단함  
- 원인 추정 5 — reasoning_effort low: 처리 1번(FIXED 먼저 검토)을 충분히 따지지 않고 바로 SQL 쪽으로 감.  
  이것은 이번 평가에서 직접 확인하지 않음(값을 바꿔 보는 실험은 코드 변경이라 하지 않음)

| R-8 | 프롬프트 수정 뒤 reasoning_effort low와 medium을 같은 평가셋으로 비교 | 설계서 24장 하이퍼파라미터 | 프롬프트만으로 부족할 때 판단 근거 | medium은 지연·토큰 증가 예상(측정 필요) |

- 우선순위 제안: R-1 → R-2 → R-4 → R-6 순. 모두 시스템 프롬프트 글만 바꾸는 일이라 코드 영향이 없음  
- 하지 않기를 권하는 방법: 키워드 규칙(`KEYWORD_RULES`)을 LLM 앞에 두어 FIXED를 강제하는 것.  
  이번 평가셋에서 키워드 규칙은 FIXED 문항 48개 중 24개만 맞히고, NL2SQL 질문 10개 중 9개를 정형쿼리로 잘못 잡음.  
  지금처럼 LLM 실패 시 대체 경로로만 쓰는 것이 맞음  
- 수정 후 확인 방법: 같은 평가셋으로 `run_routing_eval.py --pass-label v2`를 다시 돌려 이 보고서 3.1 ~ 3.2 표와 비교
